# 운영 및 장애 대응 가이드

## 배포 전 확인

```powershell
python -m unittest discover -s tests -v
python -m compileall -q api scripts
python scripts/check_secrets.py
```

Preview에 먼저 배포해 `/api/blueprint`의 정상·빈 입력·오류 응답을 확인한 뒤 Production으로 승격한다. Preview와 Production은 변수 이름은 같게, 키와 사용 한도는 분리한다.

## Vercel 진단

```powershell
vercel inspect <deployment-url> --logs
vercel logs --level error --since "1 h"
vercel logs --follow
vercel redeploy <deployment-url>
```

- 빌드 실패: Project → Deployments → 배포 선택 → Build Logs에서 Python 버전, 의존성 설치, 함수 번들 오류를 확인한다.
- 실행 실패: Project → Logs에서 route `/api/blueprint`, status `4xx/5xx`, environment, branch로 필터링한다.
- 개별 요청: Request ID를 열어 함수 실행 시간, 메모리, 외부 OpenAI 요청과 오류 메시지를 확인한다.
- 수정 후: Preview 재배포 → 테스트 입력 호출 → 오류 로그 없음 확인 → Production 승격 순서로 복구한다.

## 상태 코드별 대응

| 상태 | 사용자 메시지 | 개발자 확인 |
| --- | --- | --- |
| 400 | 입력 내용을 확인해 주세요 | JSON과 `idea` 길이 |
| 413 | 입력이 너무 깁니다 | 요청 본문 8KB 제한 |
| 502 | AI 응답을 만들지 못했습니다 | OpenAI 오류와 JSON 파싱 로그 |
| 503 | AI 설정이 완료되지 않았습니다 | `OPENAI_API_KEY` 환경변수 |
| 504/브라우저 timeout | 응답이 지연됐습니다 | 함수 실행 시간과 외부 요청 지연 |

사용자 메시지는 키·스택·원문 예외를 노출하지 않는다. 개발용 세부 정보는 Vercel 로그에서 Request ID로만 확인한다.

### 오류 응답 계약

모든 오류는 `Content-Type: application/json`과 한 개의 공개 메시지만 반환한다.

```json
{"error": "아이디어를 입력해 주세요."}
```

| 구분 | 판별 | 복구 |
| --- | --- | --- |
| 브라우저 네트워크 실패 | 응답 객체 없이 `fetch` 예외 | 연결 확인 후 같은 입력 재시도 |
| HTTP 4xx | 응답 `ok=false`, 입력 관련 메시지 | 입력 수정 후 재요청 |
| HTTP 5xx | 응답 `ok=false`, 서버 메시지 | Request ID 기록 후 운영 로그 확인 |
| 브라우저 시간 초과 | `AbortController` 중단 | 잠시 후 재시도, 반복 시 함수 지연 확인 |

### 계층별 확인 책임

| 계층 | 첫 확인 위치 | 확인 항목 | 담당 역할 |
| --- | --- | --- | --- |
| HTML/CSS | Pages 배포와 DevTools Elements | 파일 200, 레이아웃, 접근성 | 프론트엔드 |
| JavaScript | DevTools Console·Network | 요청 URL, 상태 코드, CORS, abort | 프론트엔드 |
| Python 함수 | Vercel Runtime Logs | 입력 검증, 예외 종류, 실행 시간 | 백엔드 |
| OpenAI | Vercel 로그와 OpenAI 사용량 | 인증, rate limit, 모델, 비용 | AI 운영 |

### 확인된 장애 사례

2026-08-14에 README의 예정 API 주소를 GET/POST로 확인했으나 모두 HTTP 404 `DEPLOYMENT_NOT_FOUND`를 반환했다. 이는 애플리케이션 내부의 400/5xx 오류가 아니라 Vercel 배포 자체를 찾지 못한 상태다. 우선 Vercel 프로젝트 연결과 Production 도메인을 확인하고, 배포 복구 후에만 OpenAI 키와 함수 로그를 진단한다.

## 키 유출 사고 대응

1. 노출 키를 즉시 폐기하고 새 키를 발급한다.
2. Preview와 Production 환경변수를 각각 교체한다.
3. 관련 배포를 재실행한다.
4. `git log -p`와 Actions 로그에서 최초 노출 시점과 복제 범위를 조사한다.
5. 공개 기록을 정리했다면 협업자에게 브랜치 재동기화를 공지한다.
6. OpenAI 사용량·결제 로그를 확인하고 비정상 사용을 기록한다.
7. `scripts/check_secrets.py`, GitHub Actions, 정기 키 회전으로 재발을 막는다.

### 키 관리 체크리스트

| 환경 | 등록·교체 담당 | 검토 | 원칙 |
| --- | --- | --- | --- |
| Local | 개발자 본인 | 커밋 전 secret scan | `.env`만 사용 |
| Preview | 프로젝트 관리자 | PR 배포 검증자 | 테스트 키·낮은 한도 |
| Production | 프로젝트 관리자 | 배포 승인자 | 운영 키·사용량 알림 |

키를 볼 수 있는 사람을 최소화하고, 교체 일시·담당자·영향 배포만 기록한다. 키 값 자체는 이력에 남기지 않는다.

### 운영 목표와 측정

아래 수치는 실측값이 아니라 첫 운영 주기의 `target`이다. 배포 후 고정 입력 10건으로 측정해 실측 열을 채운다.

| 지표 | target | 경고·중단 기준 | 실측 |
| --- | --- | --- | --- |
| API p95 응답 시간 | 15초 이하 | 18초 초과 경고, 20초 브라우저 중단 | 미측정 |
| JSON 스키마 성공률 | 95% 이상 | 90% 미만이면 프롬프트 롤백 | 미측정 |
| 입력당 재시도 | 최대 1회 | 반복 오류 시 자동 재시도 중단 | 코드 적용 |
| 월 사용량 | OpenAI 프로젝트 예산 내 | 80% 알림, 100% 호출 차단 검토 | 미측정 |

프롬프트 버전별로 같은 입력 세트를 사용하고 모델, 입력·출력 토큰, 응답 시간, 스키마 성공 여부만 기록한다. 실제 가격과 비용은 측정 시점의 OpenAI 사용량 보고서를 기준으로 계산한다.

## 확장 마이그레이션 체크리스트

1. `js/app.js`에서 API 호출을 `api-client.js`로 먼저 분리하고 기존 동작 테스트를 유지한다.
2. 폼 상태를 `form-state.js`, DOM 생성을 `result-view.js`로 분리한다.
3. 인증 도입 전 사용자·청사진 데이터 모델과 보존 기간을 결정한다.
4. 캐시는 비밀정보를 키에 포함하지 않고 TTL·무효화 규칙부터 정의한다.
5. 20초를 넘는 작업에만 큐와 상태 조회 API를 도입한다.
6. 단계마다 Preview에서 회귀 테스트하고 한 단계씩 Production에 승격한다.

## 프레임워크 도입 판단

| 선택 | 장점 | 단점·변경 범위 |
| --- | --- | --- |
| Vanilla 유지 | 빌드 없음, 작은 번들, 학습 구조 명확 | 화면·공유 상태가 늘면 수동 DOM 관리 증가 |
| React/Vue 도입 | 컴포넌트 재사용, 라우팅·상태 생태계 | 빌드 도구 추가, HTML을 컴포넌트로 이전, JS 상태 로직 재작성, CSS 범위 재구성 |

라우트 5개 이상, 공유 상태 3개 이상, 같은 UI 패턴 반복이 발생할 때 프레임워크 전환 비용을 다시 산정한다.

전환 시에는 `index.html`을 컴포넌트 트리로 분해하고, `js/app.js`의 API·상태·뷰 책임을 각각 모듈로 옮긴다. 이후 DOM 단위 테스트를 컴포넌트 테스트로 바꾸고, 정적 파일 검사를 빌드·lint 검사로 교체하며, GitHub Actions에 의존성 캐시와 프로덕션 빌드를 추가한다. 기존 Python API 계약은 유지해 프론트 전환과 백엔드 변경을 분리한다.
